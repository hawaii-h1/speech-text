# SpeechText

macOS menu bar voice-to-text app. Records audio via a global hotkey, transcribes speech, and pastes the result at the cursor position in the previously active app.

The app was called **VoicePeter** until the 2026 rebrand, and the rebrand itself first shipped the name misspelled (**SpeachText**). Both steps moved the bundle identifier (`com.voicepeter.app` → `com.speachtext.app` → `com.speechtext.app`), and macOS keys microphone, speech-recognition and accessibility grants to it, so each change re-asks for all three. Two one-shot migrations keep the rest from reading as a factory reset, and both walk a *chain* of old names rather than a single one: `TranscriptionHistory.adoptPreRenameStore()` moves the newest surviving Application Support folder (`SpeachText/`, else `VoicePeter/`) to `SpeechText/`, and `adoptPreRenameDefaults()` (Settings.swift) copies `SettingsKeys.portable` out of `com.speachtext.app`, then `com.voicepeter.app` — API keys, shortcuts and prompt presets included — newest domain first, never overwriting a key already present. `hasRegisteredLaunchAtLogin` is deliberately left behind: it records a registration made under an *old* bundle identifier, and carrying it over would leave the renamed app convinced it is already a login item when it is not.

## Build & Run

Open `SpeechText/SpeechText.xcodeproj` in Xcode and build (Cmd+B) / run (Cmd+R). No external dependencies or package managers — everything uses Apple frameworks.

`/rebuild` (`.claude/skills/rebuild/`) builds Release, installs to `/Applications/SpeechText.app`, stops every running instance under every name the app has shipped as, and relaunches it; `--status`, `--rollback` and `--tag X.Y.Z` are described in its SKILL.md.

Target: macOS (native Swift/SwiftUI). The app runs as a menu bar agent (`LSUIElement = true`) with no dock icon or main window.

Both configurations build with the **hardened runtime**, and `SpeechText.entitlements` declares every protected resource it gates (audio input, Apple Events, Contacts) — a feature that touches a new one needs its entitlement there, or it fails only in signed builds. Releases are Developer ID–signed, notarized disk images made by `scripts/package-release.sh`; pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml`, which opens a *draft* GitHub release. Credentials live only in repository secrets. `docs/releasing.md` has the one-time setup — including why the signing team must be chosen before the first public release: the team ID is part of the identity macOS keys every permission grant to.

## Tests

`xcodebuild test -project SpeechText/SpeechText.xcodeproj -scheme SpeechText -destination 'platform=macOS'` runs the `SpeechTextTests` unit-test bundle (sources in `SpeechText/SpeechTextTests/`). It is **standalone — no `TEST_HOST`, no `@testable import`**: the app is an LSUIElement agent that prompts for microphone access at launch, so hosting tests inside it would hang a headless run. Instead the test target compiles a curated subset of app sources directly (AudioBufferWriter, STTProvider, StreamingSTTProvider, RecordingConfiguration, Settings, LLMProvider, PromptPresets, TextRefinementService, MessageDelivery, TranscriptSpan, TranscriptMerge, TranscriptCleanup, InsertionLedger, DeliveryTier, DebugLog). The consequence: **a new app file that test code needs must be added to both targets' Sources phases in `project.pbxproj`** — and so must anything a file already in the subset comes to depend on, which is how `MessageDelivery` got here: it defines the `DeliveryChannel` that `TextRefinementService` parses send markers into. A file in the subset must not reach into the app's view or state graph (SwiftUI views, `AppState`, `SpeechEngine`), or the subset stops being a subset.

Covered: `PCMDownsampler` (3:1 downsample frame counts, stereo→mono downmix, resampler state across calls), `AudioBufferWriter` (write → readable 16 kHz mono file of the right duration, `noAudio` on empty, `reset`), the multipart form helpers and `multipartAudioPart`, `RecordingConfiguration`'s derivations (`streams`, `batchModel`, `batchAPIKey`, and `cloudLanguage`/`historyLocale` — Auto tells a cloud model nothing), `TextRefinementService.parse` (mode marker, code-fence stripping rules), and `TranscriptSpanLayer`'s whole state machine (a partial keeping its identity while it grows, a commit adopting it, only the increment of a cumulative `committed` becoming a span, a segment result that matches leaving the spans alone, and a `Frozen` span surviving every rewrite path), `TranscriptMerge` (a commit that restates everything replacing it, a partial reduced to what it adds, a revised word not defeating the match, and a two-word repeat left alone as speech), `TranscriptCleanup` (hesitations dropped with their punctuation, look-alike words kept, stretched letters and trailing ellipses, and the monotonicity that keeps it safe on cumulative text), `InsertionLedger` (a span found where it was recorded, followed when the document shifted around it, and *refused* when the user edited over it or when it appears twice; the shifting of neighbouring records) and `DeliveryTier` (an app whose range write is accepted but does not read back is Tier B; a send is Tier C whatever the probe says; AI mode delivers nothing early in any tier) — plus `UndeliveredRemainderTests`, which is the anti-duplication guard: what the stop still owes after spans were pasted during the recording, and nil when the final text disagrees with them instead of extending them. Tests never touch `UserDefaults` — the user's real API keys live in the `com.speechtext.app` domain — so anything that reads defaults (`RecordingConfiguration.current()`, `PromptPresetStore.load()`) is bypassed by constructing values directly.

## Architecture

All source files live in `SpeechText/SpeechText/`; the unit tests live in `SpeechText/SpeechTextTests/` (see **Tests** above). No SPM packages, no third-party dependencies.

### Core Components

- **`App.swift`** — Entry point. `SpeechTextApp` is the `@main` SwiftUI app with an empty `Settings` scene. `AppDelegate` manages the `NSStatusItem` (menu bar icon/menu) and settings window. `AppState` orchestrates recording flow, overlay/panel lifecycle, previous-app tracking, and paste-back. Also contains `ObservedOverlay`, a small wrapper view that bridges `SpeechEngine` to `RecordingOverlayView`. And `AppVersion`, the menu's first line (`1.0 (build 47 · a18a7d1 · date)`, click to copy): the commit and date come from `$(SPT_GIT_COMMIT)` / `$(SPT_BUILD_DATE)` placeholders in `Info.plist` that `.claude/skills/rebuild/scripts/rebuild.sh` fills on the `xcodebuild` line — an Xcode ⌘R build leaves them empty and the menu says `(dev)`.
- **`SpeechEngine.swift`** — the recording engine. Owns the microphone (`AVAudioEngine`, the tap, `barLevels` per-segment RMS), the per-segment `AudioBufferWriter`, the start/pause/resume/stop lifecycle, the device-change restart, and the History bookkeeping (`recordOutcome`, fed by each segment's `RecognitionOutcome`). Recognition itself is delegated to one `RecognitionSession` per segment, created in `setupRecordingSession` and cancelled in `cleanup`; the session's `.live(committed:partial:)` events become `liveText`, its `.failure` becomes `errorMessage`. State lives in a single stored `phase: RecordingPhase` (idle / starting / recording / paused(segmentInFlight:) / finishing); `isRecording`, `isPaused`, `isTranscribing` and `isStartingEngine` are computed from it, so the views and `AppState` read the same API as before. Exposes `liveText` — now a computed view over `spanLayer.segmentText` rather than a stored string — for in-progress transcription, `finalText` for completed transcription, `editedText` for the user-editable result, `pendingInsertionText` (a segment is ready for cursor insertion), and `awaitTranscription()` (resumes on the phase change whose `isTranscribing` flips false, after `finalText`/`errorMessage`/`lastRecordID` are already written).
- **`RecognitionSession.swift`** — the tier abstraction: `RecognitionSession` protocol (`start` / `feed(native:pcm16:)` / `pause` / `finish` / `cancel`, one instance per segment), `RecognitionEvent` (`.live(committed:partial:)` — kept apart rather than pre-joined so a later span layer can map them onto partial/commit/revise — and `.failure`), `RecognitionOutcome` (trimmed text, error, the segment's audio file whose ownership passes to the engine, cancelled), the `makeRecognitionSession(configuration:writer:recognizer:)` factory (the one place that knows which tier a configuration selects) and `joinedTranscript` (both tiers stitch committed + partial the same way).
- **`TranscriptSpan.swift`** — the span layer: `TranscriptSpan` (id, segment, text, and the state it is in — `provisional` / `committed` / `revised` / `settled` / `frozen` / `dropped`) and `TranscriptSpanLayer`, which turns the sessions' *cumulative* `committed` / `partial` strings into spans with identity. Pure logic — no engine, no view, no clock — so `PureLogicTests` covers the whole machine. Phase A of the chunked-transcription spec; `revise`/`freeze` are the hooks phase C's finalizing pass and the Record Window's hand edits will use.
- **`InsertionLedger.swift`** — `InsertionRecord` + `InsertionLedger`: what a sink has already been handed, where it landed, and what the sink holds there. Pure logic in both targets, covered by `InsertionLedgerTests` and `UndeliveredRemainderTests`. `resolve(span:in:)` is the "still untouched?" guard a replacement runs first; `remainder(of:)` is what the stop subtracts so a dictation delivered during the recording is not pasted a second time.
- **`DeliveryTier.swift`** — `AXTextProbe` (what the Accessibility API will let us do to the focused element) and `DeliveryTier` (`.a` / `.b` / `.c`) with the pure `resolve(isMessageDelivery:isOwnSurface:probe:)`, `deliversDuringRecording(aiMode:)` and `recordsRanges`. No AX calls of its own — `PasteService.probeFocusedText` makes them and hands the answers in, which is what keeps the decision in the test subset.
- **`TranscriptMerge.swift`** — `joinedTranscript` plus the merge the streaming tier needs: `transcriptWords` (punctuation-insensitive words anchored in their source), `transcriptOverlap` (how much of what is already held the incoming text repeats, and whether it re-states all of it), `mergedTranscript` and `transcriptContinuation`. Pure string logic, in both targets, covered by `TranscriptMergeTests`.
- **`TranscriptCleanup.swift`** — `cleanedTranscript`: drops hesitation sounds (`е-е-е`, `а-а`, `еее`, `м-м`, `хм`, `uh`, `um`) by their shape, collapses tripled lowercase Cyrillic letters ("тооо" → "то"), and turns a word-final `...` into a full stop. Lexical fillers ("ну", "типу") are kept — "типу" is also a real genitive. Pure logic, in both targets. `RecordingConfiguration.cleaned` applies it when `removeDisfluencies` is on.
- **`AppleRecognitionSession.swift`** — the on-device tier: `SFSpeechRecognizer` request/task, the 50 s chunk rotation (SFSpeechRecognitionTask stops accepting audio after ~1 min; rotation commits the live text and starts a fresh request under the running tap, discarding late callbacks by token and clearing a stale `isFinal`'s `finalText` so an early final in chunk 1 cannot swallow later chunks). `pause()` hands the joined live text back immediately (task and request stay alive for the eventual stop); `finish()` calls `endAudio` and waits ≤ 0.5 s, resolved early by `isFinal`.
- **`BatchRecognitionSession.swift`** — the upload tier: `finish()` writes the engine's writer to a file and uploads it; on failure the file is handed back in the outcome (not deleted) so the engine can archive it for a History retry. No live text; `feed` is a no-op because the engine's writer already collects the audio.
- **`StreamingRecognitionSession.swift`** — the realtime tier, a composition: wraps a `StreamingSTTProvider` *and* a `BatchRecognitionSession` fallback. `feed` sends the writer's 16 kHz bytes; events mirror into committed/partial (emitted as `.live`); a broken stream sets an internal `failure` and never surfaces as `.failure` — `finish()` then clears the ghost text and hands the segment to the wrapped batch session, which uploads the same writer's file.
- **`STTProvider.swift`** — `STTProviderType` enum (`.apple`, `.groq`, `.elevenlabs`), `BatchSTTProvider` protocol, the shared `makeBatchProvider(configuration:)` factory (used by both live recording, the streaming fallback and History retries), plus `GroqSTTProvider` (multipart POST to `api.groq.com/openai/v1/audio/transcriptions`) and `ElevenLabsSTTProvider` (multipart POST to `api.elevenlabs.io/v1/speech-to-text`), and `multipartAudioPart(for:)`, which reads the upload's filename and MIME type off the file's extension. Also `STTTuning`: every latency/quality knob the cloud providers use (the 1.0 s realtime VAD silence threshold, the 4 s `finish()` wait, the 100 ms send chunk, the 0.4 s commit padding, the 10 s pre-`session_started` buffer bound, the 0.2 s commit-reply grace, the 120 s / 300 s batch timeouts, and the `tag_audio_events=false` / `no_verbatim=true` Scribe flags), each with a doc comment saying why — so a value measured against the live service is never re-derived by feel in a second file. Includes `Data` extensions for multipart form encoding and `GroqError` for API error handling.
- **`StreamingSTTProvider.swift`** — `StreamingSTTProvider` protocol (push 16-bit PCM in, get `partial` / `committed` / `failed` events out over an `AsyncStream`), `makeStreamingProvider(configuration:)` (returns nil unless `configuration.streams`), `ElevenLabsRealtimeProvider` (WebSocket to `/v1/speech-to-text/realtime` with `scribe_v2_realtime`, `commit_strategy=vad`, `vad_silence_threshold_secs` and `no_verbatim` from `STTTuning` — the server echoes both in `session_started.config`, which the debug log prints; `finish()` sends a last chunk with `commit: true` and waits — bounded — for its transcript).
- **`RecordingConfiguration.swift`** — the settings one recording session runs with: `provider`, `locale`, the Groq and ElevenLabs keys and model IDs, read from UserDefaults once by `current(locale:)` (the locale defaults to `resolvedLocale()`, so it follows the keyboard layout) and carried through the session. Derived answers live here rather than in the factories: `cloudLanguage` (what a cloud provider is told — nil on Auto, see **Auto language detection**), `historyLocale` (what the record says the language was), `streams` (the ElevenLabs realtime model), `batchModel` (the upload model — realtime → `scribe_v1`, Apple → the Groq model, since neither exists behind an upload endpoint) and `batchAPIKey` (the key that upload will use — History retry checks it before starting instead of firing a request with an empty key). `makeBatchProvider(configuration:)` and `makeStreamingProvider(configuration:)` take it; History retry reads a fresh one so a retry honours the *current* settings.
- **`AudioBufferWriter.swift`** — Collects the segment's audio for batch STT providers and writes it to a temporary audio file via `AVAudioFile` — FLAC by default (`preferredUploadCodec`: lossless, about half the bytes of WAV, accepted by both Groq and ElevenLabs), WAV if the encoder throws. The file's extension is the contract: the batch providers pick the multipart filename and MIME type from it (`multipartAudioPart`) and the History archive keeps it, so a `.wav` archived before FLAC uploads existed still retries. Owns the session's `PCMDownsampler` (a stateful `AVAudioConverter` wrapper that turns each tap buffer into 16 kHz mono Int16) and converts *as audio arrives*, so `writeAudioFile()` is a single encoder pass over bytes that already exist rather than a conversion paid all at once at stop; `append` returns the converted bytes so the streaming provider sends the same ones. When no converter exists for the hardware format it falls back to native buffer copies converted at stop (native-format WAV as a last resort). Also cleanup of temp files.
- **`TranscriptionHistory.swift`** — `TranscriptionRecord` + an `@Observable` store persisted to `Application Support/SpeechText/history.json`, newest first and capped at 300 — `adoptPreRenameStore()` moves a pre-rename `VoicePeter/` folder there once, so the path in an old install's on-disk layout is not the one in the code. Failed and empty results keep their audio file (`.flac`, or `.wav` for older entries) under `Recordings/` for 7 days so they can be retried. `TranscriptionRecord.Refinement` records the LLM pass: `inputText` (what was actually sent — the Record Window refines its whole text area, not just one segment), `outputText`, `presetName`, `provider`/`model`, and `errorMessage` when the pass failed. `record.text` always stays the transcription before the LLM (hesitation cleanup already applied); `deliveredText` returns what the user actually received.
- **`HistoryView.swift`** — History browser (`HistoryWindow`): filterable list, retry-from-archived-audio, copy, and a two-pane “Dictated / AI output” comparison for entries that went through the LLM.
- **`LLMProvider.swift`** — `LLMProviderType` enum (`.groq`, `.anthropic`, `.openai`), `LLMChatProvider` protocol, `OpenAICompatibleLLMProvider` (one implementation covering Groq and OpenAI, which share the `/chat/completions` shape but not its parameters — see its `Dialect`: Groq takes `max_tokens`/`temperature`, OpenAI's GPT-5.x reasoning models reject both and use `max_completion_tokens`) and `AnthropicLLMProvider` (raw `POST /v1/messages`; sends `output_config.effort = low` where supported, opts into server-side refusal fallbacks on Opus 5, and treats `stop_reason == "refusal"` as an error). `LLMConfiguration` resolves provider/key/model from UserDefaults and builds the provider.
- **`PromptPresets.swift`** — `PromptPreset` model (`name`, `whenToUse`, `instructions`) and `PromptPresetStore` (JSON in UserDefaults, six built-in defaults with fixed UUIDs, plus the "default preset" pointer).
- **`TextRefinementService.swift`** — Builds the routing system prompt from the presets, sends the transcript wrapped in `<transcript>` tags, and parses the reply's leading `<<mode:NAME>>` marker (plus a wrapping code fence, if any). When message delivery is on it also appends the delivery contract to the prompt and parses the optional `<<send:CHANNEL to="…" subject="…">>` marker into a `SendIntent`. Markers are accepted in either order; a marker naming a channel that isn't on the allow-list is dropped and the text is pasted as usual.
- **`DebugLog.swift`** — `DebugLog.shared`, an `@Observable` ring buffer of the last 1000 entries, plus the free `dlog(category, message)` used throughout. Every entry also goes to `os.Logger`, so a build running outside Xcode is still readable in Console; the in-memory copy exists so the Debug Log window can show it without the user leaving the app.

### Recording Modes

- **Inline recording** — Triggered by global hotkey (default: `Ctrl+Shift+Q`). Shows a small floating overlay (`RecordingOverlay.swift`) at the bottom of the screen. On stop, transcribed text is pasted at the cursor in the previously focused app via `PasteService`. Falls back to opening the Record Window if accessibility permission is missing or the previous app couldn't be detected.
- **AI recording** — Triggered by global hotkey (default: `Ctrl+Shift+A`). Same flow as inline recording, but before pasting, the transcription is sent to an LLM by `TextRefinementService`. The dictation itself is the prompt: the model picks the best-matching prompt preset from `whenToUse` descriptions, applies that preset's instructions, and returns only the resulting text. The overlay stays up (tinted purple, with a sparkles badge) while the LLM works. Any LLM failure or refusal falls back to pasting the raw transcript, so a dictation is never lost.
- **Message delivery** (off by default, `messageSendingEnabled`) — An AI-mode dictation that names both a recipient and a channel ("надішли Оксані в телеграм, що я запізнююсь") is routed to a messaging app instead of the cursor. The LLM only reports *who* and *where*, exactly as spoken; `ContactResolver` turns that into real addresses from the user's own Contacts, and nothing is sent until the user confirms in `SendConfirmationPanel`. Every failure — no contact matched, no address for that channel, automation denied, the send itself throwing — falls back to pasting the text and says why. The Record Window's ✨ toggle shares the same LLM call, so a send marker there is parsed off and dropped: only the inline AI hotkey delivers.
- **Record Window** — Triggered by global hotkey (default: `Ctrl+Shift+W`). Opens `DirectRecordingPanel.swift`, a floating panel that auto-starts recording. The transport knob starts, pauses and resumes; the dot matrix along the bottom shows the level while recording and a sweeping comet while a provider is working. Transcribed segments land in an editable text column; while the column is still empty the transcript in progress is printed on the glass, with what has settled drawn brighter than the partial the recogniser may still take back. The button rail on the right insert-at-cursor / copies / sends to the webhook. The hotkey toggles recording when the panel is already open; ⎋ or ⌘W closes it, as does the ✕ that sits below the button rail, outside its recess. The rail's ✨ button turns on LLM processing: each time a segment finishes transcribing, the whole text area goes through `TextRefinementService` and is replaced with the result (turning it on with text already present processes it immediately), and the phosphor turns violet for as long as it is on.

### Services

- **`HotkeyManager.swift`** — Registers global hotkeys using Carbon `RegisterEventHotKey`. Supports three hotkeys (inline recording, AI recording, record window), each with configurable key codes and modifiers, distinguished inside the one Carbon handler by `EventHotKeyID.id`. Listens for `hotkeyDidChange` notifications to hot-reload shortcuts. Uses `Unmanaged` pointer for Carbon event handler callback.
- **`HotkeyRecorderView.swift`** — SwiftUI view that captures a new keyboard shortcut via `NSEvent.addLocalMonitorForEvents`. Filters out bare modifier keys and requires at least one modifier. Also contains free functions `shortcutDisplayString()` (builds display string with modifier symbols) and `keyCodeToString()` (converts virtual key codes to readable strings using `UCKeyTranslate`). Defines the `hotkeyDidChange` notification name.
- **`PasteService.swift`** — Pastes text at cursor by saving clipboard contents, setting the clipboard to the transcription text, simulating `Cmd+V` via `CGEvent`, then restoring the original clipboard after a delay. Also handles app activation (via `NSRunningApplication.activate` + AppleScript fallback) and accessibility permission checks/prompts.
- **`MessageDelivery.swift`** — `DeliveryChannel` (`.imessage`, `.mail`, `.telegram`, `.whatsapp`), `RecipientCandidate`, `DeliveryOutcome` and the send implementations. Two mechanisms hide behind one enum: Messages and Apple Mail are driven by a local AppleScript handler and complete the send (`.sent`); Telegram and WhatsApp can only be handed a deep link that opens the chat with the text staged (`.composed`), because both clients refuse to send from a URL. Also `AddressFormat` (is this string an email / phone / @handle?) and `AppleScriptRunner`.
- **`ContactResolver.swift`** — Turns the spoken recipient into addresses via the Contacts framework. Literal addresses the user dictated are used as-is; otherwise `CNContact.predicateForContacts(matchingName:)` runs first and, on a miss, a fuzzy pass over the whole address book. Telegram usernames are read off the contact card's instant-message addresses and social profiles, so no separate alias store is needed.
- **`WebhookService.swift`** — Sends transcribed text to a user-configured webhook URL via POST with JSON body (`text`, `source`, `timestamp`). Supports optional Bearer token auth. Uses completion handler pattern with `Result<Void, Error>`.

### UI

- **`MenuBarView.swift`** — `SettingsView` form: **General** (launch at login) and **Appearance** (skin picker, accent colour — shown only for the skin that supports one), then the three destinations organised as a pipeline so the independent model choices don't get confused: **Step 1 · Speech → Text** (engine picker with a plain-language subtitle, the speech model when a cloud engine is selected — Whisper for Groq, Scribe for ElevenLabs — and language), **Step 2 · Text → Text (AI)** (LLM provider, chat model, presets editor link, ready/needs-a-key status), **Step 3 · Text → Someone** (the message-delivery toggle, which channels this Mac can reach, Contacts status), **API Keys** (only the credentials the current selections use; the shared Groq key names both consumers), then shortcuts, webhook and permissions. All pickers read through a resolved `STTProviderType`/`LLMProviderType` rather than the raw stored string.
- **`SendConfirmationPanel.swift`** — `SendConfirmationView` and its key-taking `NSPanel`. Shows the channel, the resolved address (a picker when several matched), an editable subject and body, and a note saying whether the button will send or only stage. Send is ⌘⏎, cancel is ⎋, and "Paste instead" drops back to the ordinary paste. Unlike the recording overlays this panel deliberately takes focus.
- **`PromptPresetsView.swift`** — Presets editor window (`PromptPresetsWindow`): sidebar list with add/remove/reorder, detail pane editing name / "when to use" / instructions, default-preset toggle, and restore-defaults.
- **`DebugLogView.swift`** — the Debug Log window (`DebugLogWindow`, opened from the menu bar): filterable entry list with auto-scroll, copy-all and clear. It reads `DebugLog.shared` directly rather than taking a snapshot, so a session can be watched while it runs.
- **`Theme.swift`** — `AppSkin` (`minimal` / `techno`), the sizes each skin's two panels take, `AccentColor` (stored as `#RRGGBB`, since UserDefaults has no colour type) and `Semantic` for colours that mean something rather than decorate something. Also `.skinDidChange`.
- **`MinimalChrome.swift`** — the minimal skin's parts: `WaveformBarsView` (the bar meter, with its warm-up reveal and working dot-chase), `MinimalIconButton`, `PlainTextEditor`.
- **`DesignKit.swift`** — the techno skin's parts, in one place. `TechnoSkin` (every colour and the shared geometry), `SVGPathData` (a reader for the absolute-command subset of SVG path data, so shapes traced from Figma keep their raw `d` string), `LCDScreenShape` / `LCDScreen` (the notched glass and its inner shadow), `ShellBackground`, `InnerShadow`, `PlasticButton` / `ButtonRail`, `TransportKnob`.
- **`PixelDisplay.swift`** — the techno skin's dot-matrix display. `PixelMatrix` renders the grid in a `Canvas`; `PixelWaveform` drives it from `SpeechEngine.barLevels` on its own 30Hz clock; `PixelDisplayMode` collapses the engine's states into idle / listening / working, and `PixelPalette` supplies the green or (AI mode) violet phosphor together with the colour its loudest dots burn to — white for green, pale violet for AI, so the display does not lose its identity exactly when it is loudest.
- **`RecordingOverlay.swift`** — `RecordingOverlayView`, the inline strip, in **both** skins: a material capsule with a bar meter in the accent colour, or a 100×56 LCD with the cancel button — a `PlasticButton` in its `ButtonRail` recess — standing beside it. The techno strip shows no language: it was a badge that had to be read, on a surface meant to be glanced at. The panel is positioned so that the *display* lands on the screen's centre line (`AppSkin.overlayFocusX`) rather than the panel — with a button hanging off one side, centring the block would push the words off to the side of where the user is looking. Also `StatusOverlayView` (the transient failure notice) and their `NSPanel`s.
- **`DirectRecordingPanel.swift`** — the record window, in **both** skins. One set of state and actions with two `body` variants: a native toolbar-over-text-area with a capsule transport, or the design's fixed 362×284 device: the shell, the notched glass, the transport knob, the button rail, the dot matrix, and an editable text column. Contains `DirectRecordingPanelWindow` (whose chrome follows the skin too), `TextInsertionHandler` (inserts transcribed segments at the cursor, adding spaces as needed) and `LCDTextEditor` (`NSViewRepresentable` wrapping `NSTextView`, phosphor on black).
- **`Settings.swift`** — `SettingsKeys` (including `portable`, the rename allow-list), `adoptPreRenameDefaults()`, `normalizeStoredProviders()`, the model catalogues `groqModels` / `elevenLabsModels` (with `elevenLabsRealtimeModel`, the one ID that only exists behind the WebSocket), `SupportedLanguage`, `autoLanguageID`, `supportedLanguages` (Auto/English/Ukrainian), and `KeyboardChangeObserver` (a `DistributedNotificationCenter` observer registered with `.deliverImmediately`, so a layout switch reaches the app while it is in the background — which is the only state it is ever in). Also contains `resolvedLocale()` which resolves the effective speech recognition locale — when set to "auto", it detects the active macOS keyboard input source via `com.apple.HIToolbox` preferences and maps layout names to ISO 639-1 codes using the `layoutToLanguage` dictionary.

## Key Patterns

- **`@Observable` macro** — Used for `SpeechEngine`, `HotkeyManager`, `AppState`, `TranscriptionHistory` and `DebugLog` (Swift Observation framework, not Combine).
- **UserDefaults via `@AppStorage`** — All settings stored in standard UserDefaults. Keys defined in `SettingsKeys` enum.
- **`NSPanel` subclasses** — Floating panels use `.nonactivatingPanel` style so they don't steal focus from the user's active app.
- **Two skins, same capabilities** — `AppSkin` picks the chrome, never the feature set. `RecordingOverlayView` and `DirectRecordingPanelView` each keep both variants in one file, and the record window's buttons come from a single `railActions` list that both chassis render — so a button cannot exist in one skin and be quietly missing from the other. Closing the window is the one exception: techno draws its own ✕ below the rail, because minimal already has the system titlebar's close button and a second one beside it would be nonsense. Adding a third skin is a case in `AppSkin`, its two panel sizes, and a `body` branch in those two views.
- **Neutral is the default, a tint is opt-in** — `AccentColor.neutral` (an empty stored value) paints the level meter in `.primary` and the transport red, which is what the app has always looked like. An accent applied to *everything* turns a quiet sliver of glass into a coloured object, so the user has to ask for it. `Semantic.confirmation` keeps the copy/paste/send flash green regardless.
- **The accent belongs to the minimal skin only** — techno's every colour was matched against the design render, so `AppSkin.supportsAccent` keeps the user's colour out of it. AI mode's violet (`Semantic.ai`) is fixed in both skins: if it followed the accent, a user who picked violet would lose the one signal that tells a rewritten dictation from a plain one.
- **The window chrome is part of the skin** — minimal wears an ordinary titled `NSPanel`, so its rounded corners, the vibrancy behind `.ultraThinMaterial` and the close button all come from the system; reimplementing those only produces a worse copy. Techno is borderless because it draws its own moulded shell, and a titlebar there would sit on top of the moulding and swallow clicks meant for the knob. `DirectRecordingPanelWindow.applySkin()` swaps the `styleMask`.
- **Skin changes resize the window by hand** — the hosted SwiftUI reflows through `@AppStorage`, but the `NSPanel` around it does not, and the two skins are different sizes. Both panel classes observe `.skinDidChange` and call `setContentSize`.
- **One skin, two surfaces** — within the techno skin, the inline overlay and the record window are the same device. Every colour, radius and dot pitch lives in `TechnoSkin` (DesignKit.swift), so neither surface can drift from the other or from the Figma file.
- **Traced shapes keep their path data** — `LCDScreenShape` stores the two `d` strings Figma exported and scales them onto whatever rect it is given, instead of a hand translation into `Path` calls. Re-exporting a tweaked vector is then a copy-paste. The two halves are `union`ed, not merely overlaid: they share an internal edge at the knob's waistline, and the inner shadow strokes the shape, so anything less would draw a seam across the glass.
- **The knob is drawn, not exported** — `TransportKnob` rebuilds the design's layer stack (bevel → outer disc → groove → cap → glyph) in SwiftUI because the app needs the knob in states the design never drew (recording, transcribing, AI, hover, pressed) and a bitmap can't take a different glyph or tint. Its shading was matched against the design render pixel by pixel; changing a gradient stop by feel will drift.
- **The bevel is a `.background`, not a ZStack layer** — it is larger than the knob, and a `ZStack` re-proposes its final size to flexible children, so putting it in the stack silently inflates the disc to match it.
- **The display has its own clock, and bounces in place** — `PixelWaveform` runs at a fixed 30Hz and samples `barLevels` on each tick, rather than advancing when the audio tap fires: Core Audio's callback rate varies, so anything driven from it speeds up and slows down. Every column is redrawn from the *current* loudness (mean per-segment RMS, not the peak — one transient in any segment pins the peak to full height) times a hashed per-column jitter, so the grid jumps up and down like a hardware equaliser. The loudness goes through a compressive curve (`gain` then `pow(_, 0.7)`, above a noise floor) rather than a plain multiplier: raw RMS puts a normal speaking voice in the bottom row or two and reaches the top of the glass only when the user shouts. Columns ease towards their target (quicker up than down) instead of stepping onto it, the topmost dot fades in with the fraction of a row the column has grown into — eight rows are too coarse to move smoothly otherwise — and each lit dot carries a little hashed brightness variation, so the field reads as phosphor rather than as a chart. It deliberately does not scroll a history sideways: a track travelling across the glass reads as a progress bar rather than as a voice. The jitter is hashed from column and draw index instead of drawn from a random source, because a body re-evaluation has to reproduce the same grid; the rise is instant and the fall is eased, which is what keeps a syllable visible without the whole grid strobing.
- **Streaming rides alongside the audio file, never instead of it** — when the ElevenLabs model is `scribe_v2_realtime`, the fallback is *composition*: `StreamingRecognitionSession` wraps a `BatchRecognitionSession`, and the tap feeds the stream the 16 kHz Int16 bytes that `AudioBufferWriter.append` returns — one conversion serves both the file and the socket. The session keeps `committed` and `partial` apart (`RecognitionEvent.live(committed:partial:)`) and `SpeechEngine.liveText` is their join — so the Record Window's ghost text works exactly as it does for Apple. On pause/stop, `finish()` takes the stream's text; if the stream reported `failed`, or ended with nothing, the session clears the ghost text and hands over to the wrapped batch session, which uploads the same writer's file. History is written by the engine from the returned `RecognitionOutcome`, whichever half produced it. `RecordingConfiguration.batchModel` maps the realtime model ID to `scribe_v1` for that fallback (and for History retries), because the realtime model does not exist behind the upload endpoint. Whether ElevenLabs shows live text is therefore a function of the stored model (`streams`), not of the provider enum.
- **Spans, not one re-joined string** — `RecognitionEvent.live(committed:partial:)` keeps the two halves apart, and `TranscriptSpanLayer` is what they are kept apart *for*: the increment of the cumulative `committed` string becomes a span, and the commit adopts the id of the partial that was showing those words, so a sink that already drew the partial can replace it in place instead of appending a second copy. The engine no longer stores `liveText` — it feeds the layer and computes `liveText` from `spanLayer.segmentText`, which keeps the per-segment meaning the views have always had (a pause hands its segment over for insertion and the ghost text starts again) while the recording's whole timeline survives in `spanLayer.text`. States carry the rules: `settled` and `frozen` are terminal, so a segment result, a provider that restates its committed text, and (later) the finalizing pass all refuse to touch what the user edited by hand. A segment result equal to what the spans already spell settles them where they stand rather than redrawing them — the smallest version of the spec's "replace only what differs".
- **Tiers, decided once, from what the sink proved it can do** — `DeliveryTier` (DeliveryTier.swift) answers one question: what may this recording hand over while the user is still speaking? Tier A is our own surface, or a foreign app whose text the Accessibility API can read *and* re-select; Tier B is everything else (Chromium and Electron answer inconsistently for `contenteditable`, terminals never answer at all); Tier C is a message send, which takes nothing partial at all, because confirming anything less than final is not a confirmation. The probe's load-bearing step is the read-back — `PasteService.probeFocusedText` writes the selected range the element already has and compares what comes back, because Chromium returns `.success` on that write and then reports a different range, and a probe that trusted return codes would file VS Code under "correctable". The decision is pure logic so it is testable without an app to focus: `PasteService` does the AX I/O and hands the answers in as an `AXTextProbe`. It is taken once, at the start of the recording: a tier that changed halfway would mean text issued under one set of rules being corrected under another.
- **A span is issued once, and partials are issued to no one** — inline delivery pastes committed spans as they commit, which is what makes dictating into TextEdit show text while speaking. It never pastes a partial, in any tier: without a pass that can replace what a foreign app already holds, a partial pasted is a partial that can never be taken back, and that is the boundary invariant broken rather than served. Tier B's "committed only, and never rewritten" then holds by construction — `rewriteSegmentStable` reuses the first span's id, and `SpeechEngine.emitCommittedSpans` never emits an id twice — rather than by anyone remembering to check. Emission stops at the first span that is still moving, because nothing can reorder text already pasted into another app. AI mode buffers in every tier, not only Tier B: the LLM rewrites the whole dictation at the stop, so anything issued early would have to be taken back. That is also what makes Tier C right without knowing the destination when the recording starts — an AI-mode dictation is the only kind that can become a message, and it delivers nothing early either way.
- **The ledger records the document's copy, and the stop subtracts it** — `InsertionLedger` (pure logic, both targets) is what each sink keeps: where a span landed and *what the sink actually holds there*. The sink's copy, not the string sent — a text view with substitutions on or an app that normalises line endings stores something slightly different, and a guard that compared against our version would refuse every correction it was asked to make. Two uses follow. `TextInsertionHandler.replaceSpan` and (later) phase C replace a span only where `resolve` can still find it: the recorded range if the text there matches, otherwise the one *unambiguous* occurrence elsewhere, otherwise nothing at all — two identical occurrences resolve to nothing, because "the last one" is a guess and a guess may not rewrite the user's document. And `remainder(of:)` is what stops the third doubled dictation: the stop pastes the authoritative text minus what the app already has, and when the final text *disagrees* with what is there rather than extending it (a streaming segment that fell back to a batch upload and came back worded differently) it pastes nothing at all. A slightly stale dictation beats two wordings of it stacked in the document.
- **Clipboard restores coalesce across a burst** — several pastes per recording broke the save/restore pair that protects the user's clipboard: the second paste's save read back the *first paste's text*, so a second later the user's clipboard held a fragment of their own dictation. `PasteService` takes the snapshot once per burst and cancels and reschedules the pending restore instead of stacking a second one behind it.
- **Sessions, not provider branches; one per segment, the archive stays with the engine** — `makeRecognitionSession` is the only place that knows which tier a configuration selects, so `SpeechEngine` has no *per-segment* `if provider == …` recognition branches — the one remaining `provider == .apple` test in `setupRecordingSession` caches the `SFSpeechRecognizer` across sessions to keep the speech model loaded, which is exactly why it cannot live inside a per-segment session; it builds a fresh `RecognitionSession` for every segment (a resume is a new session), but the `AudioBufferWriter` and the History calls stay in `SpeechEngine`: the writer must exist for every tier (it is the batch upload, the stream's fallback *and* the archive kept when on-device recognition returns nothing), and the tap must be gone before it is dropped — `cleanup` tears the engine down before resetting the writer for exactly that reason. Sessions report; the engine records.
- **One phase enum, booleans are views over it** — the engine's state is the single stored `RecordingPhase`; `isRecording`/`isPaused`/`isTranscribing`/`isStartingEngine` are read-only computed properties. When these were four stored flags, a stop that set `isRecording = false` a line before it set `isTranscribing = true` could be observed in between as "idle" — a phase write is atomic. `@Observable` tracks the computed getters through the stored `phase`, so every view keeps updating without change. `awaitTranscription()`'s waiters resume from `phase`'s `didSet` on the `isTranscribing` true→false *edge*; `paused(segmentInFlight: true) → finishing` is deliberately not an edge, because a stop that arrives while a paused segment is still uploading is now waiting on that same segment. `segmentFinishStarted` stays a separate flag on purpose: "this segment's audio was already sent" is not a phase — it survives `paused(true) → paused(false)` and is what stops a stop-from-paused from uploading the same audio twice. `cleanup()` never writes `phase`; every caller sets `.idle` immediately before calling it, after its result fields are in place, so a resumed waiter always sees a finished result. The Debug Log shows one `phase: a → b` line per transition instead of three flag lines.
- **The socket opens before the microphone does** — `setupRecordingSession` calls `session.start()` (and so the realtime provider's `connect`) before `installAudioTap` and before the background `prepare()`/`start()`, so the TLS handshake overlaps the 100–300 ms the hardware takes. Audio the tap produces before the server's `session_started` is held in `ElevenLabsRealtimeProvider.preSessionMessages` — already encoded as socket messages, so the flush is only `task.send` calls and never stalls the audio thread (it runs under a separate `sendLock` that orders the socket's batches; holding the state `lock` across a send would deadlock against a synchronously-delivered send completion, whose `fail` → `close` path takes that same lock) — and released when it arrives, so the first syllable is neither dropped nor reordered behind later chunks; a `finish()` before the session started sends what was held ahead of the commit. If the bound (`STTTuning.streamPreSessionBufferSeconds`) fills, the stream *fails* rather than dropping the oldest audio: a transcript missing its opening seconds must not be recorded as a success, and the batch fallback has the whole segment on disk. `finish()` likewise does not trust the first `committed_transcript` it sees — the server answers in order, so a VAD segment closed just before the stop lands first — and waits `STTTuning.streamCommitGraceSeconds` for a partial that would show the final segment is still coming. The partial that shows it, though, must be a *new* one: Scribe also re-sends a segment it has just committed as one more `partial_transcript`, and taken at face value that echo both joins the same words on twice (the dictation pasted doubled) and holds `finish()` for its whole timeout waiting on a segment that will never be committed — so `ElevenLabsRealtimeProvider.isEchoOfCommitted` drops a partial equal to the last committed text. That equality is only the first frame of the echo, though: keep talking and the re-statement *grows*, arriving as the whole accumulated transcript with a word or two revised, which an equality test cannot see. So `StreamingRecognitionSession` does not join what the stream reports — it merges it (`TranscriptMerge.swift`): `mergedTranscript` replaces the committed text with a re-statement of all of it (the server's later version saw more audio) and `transcriptContinuation` reduces a partial to what it adds. Word-level comparison, punctuation-insensitive, with a `restatementAgreement` tolerance for the revised words and a `minimumRepeatedWords` floor below which a repeat is taken for speech rather than for a re-send.
- **Hesitations are cleaned before they become spans** — `no_verbatim=true` is echoed back by the server and Scribe still writes Ukrainian "е-е-е", so `SpeechEngine` runs `configuration.cleaned` on every `.live` event, on Apple's `pause()` text and on each `RecognitionOutcome`, and History retry does the same. Not at the stop: spans are pasted while the user speaks, and a stop whose text no longer extends them is read by `InsertionLedger.remainder` as disagreement and pastes nothing. That is also why `cleanedTranscript` must be monotone on whole-word extensions — a rule may rewrite a word only from that word and what came before, never edit a word already written (a filler's full stop is dropped rather than moved onto the previous word). History therefore stores the cleaned text as `record.text`: cleanup counts as transcription quality, and "raw" in the Refinement sense means "before the LLM".
- **Scribe quality flags are sent explicitly** — the upload API's `tag_audio_events` defaults to *true*, which would paste "(laughs)" into a document, so `ElevenLabsSTTProvider` sends it off; `no_verbatim=true` goes on both the upload and the realtime query string (fillers and false starts dropped server-side; documented for scribe_v2, accepted and ignored by scribe_v1). The batch model IDs in `elevenLabsModels` are exactly what the API's `unsupported_model` error lists (`scribe_v1`, `scribe_v1_experimental`, `scribe_v2`); the realtime ID exists only behind the WebSocket.
- **`.task` captures the view by value** — which is why `PixelWaveform` reads levels through a small `LevelFeed` class rather than its own stored property, and why the task is keyed on `mode`.
- **Carbon Events API** — Global hotkeys use `RegisterEventHotKey` / `InstallEventHandler` from Carbon.HIToolbox (the only way to register system-wide hotkeys on macOS).
- **No app sandbox** — Disabled in entitlements to allow accessibility APIs (`AXIsProcessTrusted`) and global event taps.
- **Clipboard preservation** — `PasteService` saves and restores clipboard contents around paste operations so the user's clipboard is not clobbered.
- **Settings are snapshotted per session** — `SpeechEngine.startRecording` reads a `RecordingConfiguration.current(locale:)` once and every later step (pause, resume, stop, the stream fallback, the device-change restart) uses that copy; only `locale` is updated, by `resumeRecording(locale:)`. Before this, each step re-read UserDefaults, so changing the engine picker while the mic was live could send the second half of a recording to a different provider than the first. Two consequences are deliberate: provider, model and API key are frozen at start, and the batch upload's `language` is the segment's `cloudLanguage` captured at start/resume rather than `resolvedLocale()` re-read at stop (the Apple path already worked that way). History retry is the exception — it reads a fresh configuration, because a retry exists to try the settings the user has *now*.
- **Stored-value normalization** — `normalizeStoredProviders()` (Settings.swift) runs at launch and from the Settings view: a `sttProvider`/`llmProvider` string that no longer maps to a case is reset, and every stored model ID is checked against its catalogue (vendors retire whole generations, e.g. OpenAI's GPT-4.x → GPT-5.6). Without it the picker finds no matching tag and renders *blank* while the engine silently falls back to its default — the UI shows nothing and the app runs something the user didn't pick.
- **Rename migrations are opt-in per key** — `SettingsKeys.portable` lists what crosses the bundle-identifier change, rather than copying the whole old domain. A blanket copy would bring `hasRegisteredLaunchAtLogin` (and the `didAdoptPreRenameDefaults` marker itself) with it, leaving the new app convinced it is already a login item when the registration belongs to a bundle identifier that no longer launches.
- **One-time shortcut migration** — `AppDelegate.migrateHotkeyLayoutIfNeeded()` clears stored hotkey values once (guarded by `hotkeyLayoutVersion`) so a changed built-in layout reaches existing installs; later customisations survive because the version has already been bumped.
- **Auto language detection is Apple's problem, not the cloud's** — On "Auto (System)" `resolvedLocale()` reads the active keyboard input source and maps it to a locale, because `SFSpeechRecognizer` must be handed one. A cloud provider is handed *nothing*: `RecordingConfiguration.cloudLanguage` is nil on Auto, and Whisper and Scribe detect the language from the audio. Forcing the layout's guess on them was a data-loss bug, not a mis-spelling — dictating Ukrainian with a US layout sent `language_code=en`, and Scribe answered with a two-second English *translation* of an eleven-second recording (History's own records: every truncated or transliterated entry carried `locale=en`, and 70 of 91 `en` records held Cyrillic text). History records `historyLocale` — "auto" when the model chose — so a record never claims a language that was never requested, and a retry takes the language from the current settings rather than repeating the guess.
- **Preset routing in one call** — The LLM both picks the preset and applies it in a single request; it reports its choice on a leading `<<mode:NAME>>` line that `TextRefinementService.parse` strips. This avoids a separate router round-trip, which matters because the user is waiting for the paste.
- **Graceful LLM degradation** — Every LLM failure path (missing key, HTTP error, refusal, empty response) falls back to the raw transcription rather than producing nothing, surfaces a status overlay, and is written to the history entry so a silently-unrewritten paste is explainable after the fact.
- **Attaching the LLM pass to a history entry** — `SpeechEngine` writes the history record, but refinement happens later in `AppState`/`DirectRecordingPanelView`. The engine exposes `lastRecordID` (cleared on each new session) so the LLM step can update that entry instead of creating a second one. A successful retry clears any refinement, since it described text that no longer exists.

- **The model names the person, never the address** — The delivery prompt forbids inventing or "correcting" a phone number, email or username, because an LLM asked for an address will produce a plausible one. The transcript's recipient string goes to `ContactResolver` verbatim; a wrong result is then a visible wrong *match* in the confirmation panel rather than an invisible wrong number.
- **Fuzzy contact matching is not a nicety here** — Contacts' own name predicate matches from the start of a name component, so a Ukrainian dictation in any oblique case ("Оксані", "Петренку") never matches the card. The fallback pass folds diacritics and scores by edit distance, where one or two letters of case ending cost little.
- **Confirmation before every send** — Dictated names are exactly what speech-to-text gets wrong, and a sent message can't be recalled. The panel is the gate, and it is honest about which side of the line each channel is on: "Send" for the scripted ones, "Open" for the deep-link ones.
- **Apple event parameters, not string interpolation** — `AppleScriptRunner` calls a handler with real string parameters instead of building the script text around the message. Interpolating a dictation would break on the first quote, backslash or newline in it.
- **Deep links are percent-encoded by hand** — `URLComponents.queryItems` leaves `+` raw, and Telegram and WhatsApp decode a raw `+` back into a space, so a dictated "5+3" would arrive as "5 3". `MessageDelivery.encodedQuery` encodes the values itself so the message arrives as confirmed.

## Permissions Required

- **Microphone** — For audio capture (`AVAudioEngine`). `requestMicrophoneAccess` runs from `applicationDidFinishLaunching`.
- **Speech Recognition** — For Apple on-device STT (`SFSpeechRecognizer`). There is no explicit `requestAuthorization` call: the system raises the prompt the first time an Apple segment starts a recognition task, so a user who only ever runs a cloud engine is never asked for a permission the app would not use. `NSSpeechRecognitionUsageDescription` is in Info.plist for that prompt.
- **Accessibility** — For simulating `Cmd+V` paste via CGEvent. Must be granted in System Settings > Privacy & Security > Accessibility. `AppDelegate` prompts at every launch where it is not already granted (not once ever): the grant is revocable and is attached to the app's code signature, so a rebuild or an OS update can silently drop it, and a paste that quietly does nothing is the failure this avoids.
- **Contacts** (`NSContactsUsageDescription`) — Only for message delivery: looking up the person named in a dictation. Requested the first time a send is attempted.
- **Automation** (`NSAppleEventsUsageDescription`) — Only for message delivery to Messages and Apple Mail. macOS asks per target app on the first send; a refusal surfaces as `DeliveryError.automationDenied` and the text is pasted instead.
